# Development planner（开发计划生成器）

帮助用户产出**可执行**的开发计划。核心不是堆砌文字，而是：**先澄清，再结构化输出**，任务按**最小可迭代**与**垂直切片**拆分。

## Quick Reference

| 阶段 | 关注点 | 关键问题 |
|------|--------|---------|
| P0 | 改动范围 | 要做什么？边界在哪？验收标准？ |
| P1 | 设计方法 | 架构/模式？技术栈约束？ |
| P2 | 核心设计 | 关键抽象？数据流？职责划分？ |
| P3 | 修改权限 | 运行时代码？基础库？工具链？ |

**约束**：总计 5-12 个问题，从 P0 开始逐组问，信息足够可跳过后续组。

**输出职责**：本 skill 负责澄清和任务拆分；正式计划成品需交给 `plan-mode-plan-writer` 统一补齐上下文、落地保存并返回路径。

## When to use

- 用户需要开发计划、里程碑、任务拆分、范围界定、迭代规划。
- 用户提出"帮我制订开发计划：实现/改造……（某模块/某文件/某方法）"这类请求，且希望拆成可执行任务。
- `brainstorming` 已完成设计收束，需要将设计文档转化为开发计划。
- 信息不完整时，须先澄清再输出计划，或显式列出 Assumptions。

## Workflow

### Step 1: Clarification first

在规划前**必须先提问**，除非用户已提供极其完整的信息。

**提问顺序（按 P0→P3 优先，不得打乱优先级）：**

1. **P0 改动范围（Scope）**：本次要做什么、边界、成功标准。
2. **P1 设计方法与编程工具（Approach & tooling）**：采用的架构/模式、Unity/C# 与既有工具链/工程化约束。
3. **P2 核心设计思路（Core idea）**：关键抽象、数据流与职责划分、设计动机（为什么这么拆）。
4. **P3 是否允许修改（Permission）**：仅将用户**明确许可**的类型纳入计划；常见维度见下方清单。

**原则：**

- 总问题数控制在 **5–12 个**；从 P0 问起，该组信息已足够时可略过后续组的问题。
- 使用**分组**呈现；每组通常 **2–3 个**高价值问题即可。

**P0–P3 问题清单（可裁剪，按组选用）：**

- **P0 改动范围**
  - 这次要解决的具体问题/目标是什么？验收标准是什么？
  - In Scope / Out of Scope 是否有明确边界？最不希望触碰的模块是哪些？
- **P1 设计方法、编程工具**
  - 希望采用的设计方法或模式是什么（例如垂直切片、事件驱动、数据驱动、分层等）？
  - 技术栈与工具约束是什么（Unity 版本、C# 版本、是否允许 Editor 扩展等）？
- **P2 核心设计思路**
  - 期望的核心抽象与模块边界是什么？关键数据流或生命周期如何走？
- **P3 是否允许修改**（逐项需用户明确 yes/no，未答则不得当作默认可改）
  - **产品/玩法运行时代码**（本次需求直接相关的业务逻辑与功能代码）
  - **项目框架/共享基础库与公共 API**（被多模块复用的 utils/framework/base、跨域契约、通用组件）
  - **基础工具链与工程化**（构建/打包/发布/CI、代码生成、编辑器/开发工具、脚本工具等）
  - **项目结构与边界**（目录结构、程序集/模块边界、命名空间、对外接口稳定性）

**若用户未回答：** 可做合理假设，但必须在输出中单独列出 **Assumptions**，不得隐含。

**未获用户明确许可时：** 不得将「项目框架/共享基础库与公共 API」「基础工具链与工程化」「项目结构与边界」纳入默认可改范围。
若计划仍依赖此类改动，必须在 **Assumptions** 中写明，并建议在 **Risks & Open Questions** 中标注为待确认项（最好附带不改基础的替代方案/降级方案）。

### Step 2: Generate the plan

在澄清完成后，先生成 **计划内容骨架**，再交给 `plan-mode-plan-writer` 整理成正式计划文件。

最低要求仍是：**Background**、**Scope**、**Tasks**；但如果该计划最终会进入正式落地阶段，必须额外补充执行上下文（当前状态、关键文件、验证方式、handoff 信息等）。

## Background

须覆盖：

- 为什么要做（问题 / 机会）
- 当前现状
- 目标与预期收益

建议条目：

- 当前问题：
- 目标：
- 预期收益：

---

## Scope

### In Scope

- 逐项列出可交付能力，尽量**可验证**（能判断是否完成）。

### Out of Scope

- 明确写出**不包含**的内容，防止范围膨胀。

---

## File Structure

在定义 Tasks 之前，先列出本次改动涉及的文件及其职责。这是分解决策被锁定的地方。

- 每个文件应有单一清晰职责
- 一起变更的文件应放在一起
- 在已有代码库中，遵循已有模式；如果某个需要修改的文件已变得过大，在计划中包含拆分是合理的

```markdown
## File Structure

- `路径/to/file.cs` — 职责说明
- `路径/to/another.cs` — 职责说明
```

---

## Tasks（拆分原则）

### Principle 1: MVP-first（最小可迭代）

每个 Task 须：

- 可**独立完成**
- **可验证**

### Principle 2: Vertical slice（垂直切片）

错误示例（纯技术分层）：先写GameData和PlayerData、再写ViewModel、最后写View

正确示例（用户价值）：在存档内新增status字段，并在View上展示出status信息

### Principle 3: Uniform task shape

每个任务使用统一结构：

```text
### Task N: <名称>
- 目标：
- 输入：
- 输出：
- 涉及文件：
- 验收标准：
  - ...
```

**示例（可复制到计划正文）：**

```markdown
### Task 1: 用户可以注册账号

- 目标：实现基础注册流程
- 输入：邮箱 + 密码
- 输出：成功创建用户账号
- 涉及文件：
  - Create: `src/auth/register.ts`
  - Modify: `src/api/users.ts`
  - Test: `tests/auth/register.test.ts`
- 验收标准：
  - 用户可以提交注册表单
  - 数据成功写入持久化层
  - 用户收到成功反馈
```

## 澄清问题模板（可复制）

向用户发起澄清时，可直接粘贴并按实际情况删改未需要的条目；总题数仍建议 **5–12** 个。

```markdown
### 澄清问题（按 P0→P3 顺序）

**P0 改动范围**
- 本次要解决的具体问题/目标是什么？验收标准是什么？
- In Scope / Out of Scope 是否有边界？哪些模块明确不要动？

**P1 设计方法、编程工具**
- 希望采用的设计方法或模式是什么？
- 技术栈与工具约束是什么（Unity/C#、工程化工具链、是否允许 Editor 扩展/开发工具变更等）？

**P2 核心设计思路**
- 核心抽象与模块边界期望是什么？关键数据流或生命周期怎么走？

**P3 是否允许修改**（请逐项回复是否允许）
- 产品/玩法运行时代码（业务逻辑与功能代码）：
- 项目框架/共享基础库与公共 API（framework/base/utils、跨域契约等）：
- 基础工具链与工程化（构建/CI/代码生成/编辑器或开发工具等）：
- 项目结构与边界（目录/程序集/模块拆分、对外接口稳定性）：
```

### Step 3: Hand off to `plan-mode-plan-writer`

当计划已经 decision-complete 时：

1. 使用本 skill 产出清晰的范围、任务、验收标准
2. 使用 `plan-mode-plan-writer`：
   - 补齐弱模型执行上下文
   - 保存到 `.agents/plans/`
   - 在回复中告知用户路径

如果当前只是在澄清阶段或草案阶段，不要提前落地保存。

## Optional enhancements

**Phases：** 任务较多时按阶段组织，例如：

- Phase 1: MVP
- Phase 2: 增强功能
- Phase 3: 优化 / 扩展

**Risks & open questions：**

```markdown
## Risks & Open Questions

- ...
```

**Assumptions（信息不足或用户未答澄清问题时必填）：**

```markdown
## Assumptions

- ...
```

---

## No Placeholders

每个 task 的验收标准和输出必须包含实际内容，不得使用占位符。以下都是**计划失败**：

- "TBD"、"TODO"、"后续补充"
- "完成实现"、"按需求完成"
- "添加适当的错误处理"（没有具体说明）
- "类似 Task N"（直接复制内容 — 执行者可能乱序阅读）

---

## Self-Review

写完完整计划后，用 fresh eyes 对照需求自检：

1. **需求覆盖：** 逐项检查需求/设计文档，每个条目都能指向一个 task 吗？列出缺口。
2. **占位符扫描：** 搜索计划中的红旗 — 任何 "No Placeholders" 中列出的模式。发现则修复。
3. **一致性检查：** 后续 task 中使用的类型、方法签名、属性名与前面定义的一致吗？Task 3 叫 `clearLayers()` 但 Task 7 叫 `clearFullLayers()` 是 bug。

发现问题直接修复即可，不需要再次审阅。

---

## Role prompt（行为约束摘要）

以资深技术负责人身份协助用户制定清晰、可执行的计划：

1. 信息不完整时，**按 P0→P3 顺序**提出 5–12 个关键澄清问题：**P0** 改动范围，**P1** 设计方法与编程工具，**P2** 核心设计思路，**P3** 是否允许修改（产品/玩法运行时代码、项目框架/共享基础库与公共 API、基础工具链与工程化、项目结构与边界）。用户未明确许可前，**不得假定**可改「基础工具/工程化」「项目框架/共享基础库/公共 API」「结构边界」；若计划依赖此类改动，写入 **Assumptions**，并在 **Risks & Open Questions** 中标注待确认，同时给出不改基础的替代路径。
2. 输出必须包含 Background、Scope（In / Out）、Tasks。
3. Tasks 按 MVP-first 拆分；每个任务可独立、可验证；优先垂直切片而非技术分层。
4. 信息不足时列出 Assumptions；必要时按 Phase 分阶段。
5. 避免模糊表述，验收标准须具体可执行。
6. 在拆 Tasks 前先列 File Structure；验收标准中禁止占位符；计划完成后执行 Self-Review。

## Anti-patterns

| 错误 | 正确 | 原因 |
|------|------|------|
| 未澄清范围就输出完整计划 | 先按 P0→P3 收集关键信息 | 避免计划偏离真实目标 |
| 把基础库/工具链默认纳入可改范围 | 未获许可时列为待确认或替代方案 | 避免越权规划 |
| 按技术分层拆任务 | 按可验证的垂直切片拆任务 | 便于迭代和验收 |
| 验收标准写成"完成实现" | 写出可观察行为或检查命令 | 计划才可执行 |
| 输出完计划就结束 | 正式计划交给 `plan-mode-plan-writer` 落地保存 | 否则无法稳定交接 |
| 跳过 File Structure 直接拆任务 | 先列出涉及文件及职责再拆任务 | 便于分解决策和 review |
| 验收标准含 TBD/TODO | 验收标准写具体可验证内容 | 否则执行者无法判断是否完成 |

## Checklist

- [ ] 已明确目标、范围和成功标准
- [ ] 已区分 In Scope / Out of Scope
- [ ] 已列出 File Structure（涉及文件及职责）
- [ ] 已记录必要 Assumptions
- [ ] Tasks 可独立完成且可验证
- [ ] Tasks 验收标准不含占位符
- [ ] 未默认纳入用户未授权的基础库、工具链或结构边界改动
- [ ] 已执行 Self-Review（需求覆盖、占位符、一致性）
- [ ] 正式计划已交给 `plan-mode-plan-writer` 统一落地
