参考辐射（Fallout）和博德之门（BG3）的无道德评判选择系统，为 Tactics 的 roguelike 探索层设计一套"没有裁判"的选择框架。

## 辐射/博德之门的无道德选择哲学

辐射和博德之门的核心不是"没有后果"，而是**没有裁判**。游戏不告诉你什么是"好"选择、什么是"坏"选择——只有**后果**，没有**评判**。

### 核心设计原则

1. **取消道德计分板**
   - ❌ 善良/邪恶条、Karma值、Paragon/Renegade分
   - ✅ 只有**结果**：谁活了、谁死了、谁恨你、谁欠你

2. **每个选择都是"两种正确"的碰撞**
   - ❌ "救小孩" vs "杀小孩"（这不是选择，是道德测试）
   - ✅ "救小孩但村庄被毁" vs "牺牲小孩但全村得救"（这才是选择）

3. **信息不对称**
   - 玩家永远不知道"另一个选项会怎样"
   - 事后可能发现你以为的善举造成了灾难

4. **派系声誉 ≠ 道德**
   - 每个派系有自己的价值观，讨好A必得罪B
   - 不存在"所有人都爱你"的最优解

### Roguelike 结构的约束与优势

**约束**：
- 单局 30-45 分钟，玩家不会反复读档
- 没有长期 NPC 关系网（不像 CRPG 有上百小时的伙伴系统）
- 事件发生在节点上，是离散的

**优势**：
- 短局意味着选择可以更**激烈**、后果更**即时**
- 不需要铺垫 20 小时的角色弧——选完立刻看到后果

## 四个设计方向

### 方向 A：价值冲突型

> 不是"好 vs 坏"，而是"你的价值观 vs 别人的价值观"

**示例事件链**：

```
[区域1 事件] 腐败森林中的营地
你发现一群堕落罗格围着一个绑在树上的商人。
商人喊道："救我！他们要把我献给树！"
罗格首领："外来者，这不是你的事。离开，我们放你走。"

选项1: [力量 60%] 冲进去杀光罗格
  → 成功: 商人获救，给你 3 金币 + 地图标记
  → 失败: 商人死于混战，你受到伤害，罗格仇恨你

选项2: [魅力 55%] 谈判
  → 成功: 罗格放人，商人欠你人情（区域3回报）
  → 失败: 罗格觉得你在耍他们，开战

选项3: 离开（无需判定）
  → 商人死了。但罗格以后不会主动攻击你。
      你在区域2发现商人的遗物（2金币），没人拿。
```

**关键设计**：每个选项都有合理动机（道德、功利、生存），没有"正确"答案。

### 方向 B：信息赌注型

> 你的选择基于**不完整信息**，事后才知道真相

这个方向特别适合 Roguelike，因为每次 Run 可以改变"真相"。

**示例**：

```
[区域2 事件] 墓地中的低语
你在一个打开的墓穴旁听到低语声。
里面传出声音："外来者...把匕首放回我的胸口，我会给你力量。"
墓穴旁有一把生锈的匕首和半页日记。

选项1: [体质 50%] 把匕首放回尸体胸口
  → 成功: 尸体安息，你获得古老的祝福（+属性）
  → 失败: 尸体暴起，战斗

选项2: 读日记，寻找真相
  → 日记揭示：死者是吸血鬼猎人，匕首是封印吸血鬼的圣物
  → 现在你有完整信息——但仍然有选择：
    a) 带走匕首（获得武器，但释放吸血鬼）→ 区域3遇到那个吸血鬼
    b) 加固封印（匕首消失，但吸血鬼不会出现）→ 区域3少了这个怪
```

**关键设计**：第一层选择是"盲选"，第二层（如果选择调查）给更多信息。寻求真相对玩家有利，但有成本。

### 方向 C：两难困境型

> 你必须选一个，不能全都要

```
[区域3 事件] 修道院地牢
你同时听到两个方向的求救声。
左：一个修女被铁链锁住，"救救我，我知道女王的弱点！"
右：一个骑士被关在笼子里，"我可以帮你打女王，只需要放我出来！"
时间紧迫，你只能救一个——另一个会被女王的巡逻队杀死。

选项1: [敏捷 60%] 救修女
  → 成功: 修女告诉你女王弱点（Boss战+25%伤害）
  → 失败: 救人失败，巡逻队来了，被迫战斗
  → 修女获救，骑士死亡

选项2: [力量 65%] 救骑士
  → 成功: 骑士加入你的队伍作为临时盟友（Boss战帮手）
  → 失败: 同上
  → 骑士获救，修女死亡

选项3: 尝试两个都救 [敏捷70% AND 力量70%，双判定]
  → 两判定都成功：两人都获救（极低概率）
  → 任一失败：两人都死 + 你受伤
```

**关键设计**：和/或逻辑创造有趣的博弈，没有第三选项能完美解决（除了极小概率的赌博）。

### 方向 D：跨区域后果

> 你现在的选择，会在 20 分钟后回来找你

```
Run 过程:

区域1 [选择]: 你遇到一个逃亡的堕落罗格，他说他不想再为女王服务。
          → 放走: 他感激你，走了
          → 杀掉: 获得 2 金币

... 15 分钟游戏后 ...

区域3 [后果]:
  放走分支 → 那个罗格现在是女王副手，记忆你的恩情
           → Boss战开始前，他帮你放倒一个精英怪
  杀掉分支 → 他永远不会出现了，那个精英怪还在

或者:
  放走分支 → 他骗了你，他现在是女王的间谍
           → 你之前在区域2选的路线被他泄露给女王
           → 区域3的敌人配置更强
  杀掉分支 → 你避免了背叛，但错失了一个可能的盟友
```

**关键设计**：后果延迟但不可逃避，每次 Run 的后果不同（增加重玩性）。

## 融合方案：Tactics 无道德选择框架

综合四个方向，提出统一框架：

> **不用"好/坏"标签，用"代价/回报"结构。每个选择都有价签，玩家自己决定付什么。**

### 核心模型：代价三轴

| 代价类型 | 含义 | 示例 |
|----------|------|------|
| **即时代价** | 立刻被影响的东西 | HP损失、金币消耗、属性暂时下降 |
| **延迟代价** | 后面才会兑现 | Boss变强、某个门打不开、NPC态度改变 |
| **机会代价** | 你放弃的东西 | 救了A就不能救B、拿了宝箱就错过祝福 |

### 事件设计模板

```
┌─────────────────────────────────────────┐
│  事件标题                                │
│  情境描述（不暗示对错）                    │
├─────────────────────────────────────────┤
│  选项A: [属性判定 XX%]                   │
│    代价: 即时(HP-5) / 延迟(区域3敌人+1)   │
│    回报: 即时(金币+3) / 延迟(NPC帮助)      │
│                                          │
│  选项B: [属性判定 YY%]                   │
│    代价: ...                             │
│    回报: ...                             │
│                                          │
│  选项C: 离开（无判定，无即时得失）          │
│    代价: 机会（错过A和B的回报）             │
│    回报: 安全（无风险）                    │
└─────────────────────────────────────────┘
```

**关键原则**：
- "离开"永远是一个有效选项，不是"懦弱"
- 代价和回报永远**同时存在**——没有只有回报的选择
- 每个选项都**值得选**，取决于你的当前状态

---

## 决策一：代价粒度

### 两种模式对比

| 维度 | 粗粒度（辐射式） | 细粒度（杀戮尖塔式） |
|------|----------------|---------------------|
| 单次选择影响 | 大——一个决定可能改变区域走向 | 小——每次选择是微调 |
| 玩家感知 | "我做了一个重大决定" | "我一直在做小选择" |
| 设计复杂度 | 高——每个大选择都需要完整分支 | 低——小选择可以复用模板 |
| 重玩价值 | 高——不同选择走完全不同的路 | 中——累积效应有差异但大方向相似 |
| Roguelike适配 | 需要大量内容填充分支 | 天然适合——30分钟Run内多次微选择 |

### 结论：粗粒度为主，细粒度为辅

```
每层地图：1个"微事件"（细粒度，10秒决定）
   ↓ 累积
每个区域：1个"关键事件"（粗粒度，影响区域走向）
   ↓ 累积
整个Run：3-4个"命运转折点"（粗粒度，影响结局）
```

**微事件**：代价小、决定快、风险低
- "打开宝箱还是跳过？" → 代价：可能触发陷阱 / 回报：金币
- "休息恢复HP还是继续探索？" → 代价：时间（错过后续节点）/ 回报：安全

**关键事件**：代价大、需要思考、风险高
- "救商人还是杀商人？" → 代价：延迟后果（区域3变化）/ 回报：即时收益
- "走左边（危险但富饶）还是右边（安全但贫瘠）？" → 代价：机会成本

**命运转折点**：不可逆、定义整局走向
- "进入修道院前，选择先去墓地还是先去森林？" → 决定你遇到哪些事件
- "Boss战前，选择正面进攻还是偷袭？" → 决定Boss战配置

## 决策二：Run 变量系统

### 需要追踪的状态类型

| 状态类型 | 示例 | 用途 |
|----------|------|------|
| **NPC存活** | `merchant_alive: true/false` | 决定后续事件是否出现 |
| **玩家选择** | `spared_rogue: true/false` | 决定后续事件的分支 |
| **物品持有** | `has_holy_dagger: true/false` | 解锁特定选项 |
| **数值累积** | `reputation_forest: 3` | 影响NPC态度 |
| **事件完成** | `completed_altar_001: true` | 防止重复触发 |

### 三种方案对比

**方案A：纯布尔标记**
```json
{
  "merchant_alive": true,
  "spared_rogue": false,
  "has_holy_dagger": true
}
```
- ✅ 最简单，编辑器容易实现
- ✅ 调试容易
- ❌ 无法表达"程度"或"多个状态"

**方案B：枚举标记**
```json
{
  "merchant_status": "saved",  // "saved" / "killed" / "ignored"
  "rogue_status": "spared",    // "spared" / "killed" / "betrayed"
  "holy_dagger": "secured"     // "secured" / "taken" / "destroyed"
}
```
- ✅ 表达力更强，语义清晰
- ❌ 编辑器需要枚举下拉框

**方案C：数值+布尔混合**
```json
{
  "merchant_alive": true,
  "merchant_gratitude": 2,
  "forest_reputation": 3,
  "has_holy_dagger": true
}
```
- ✅ 最灵活
- ❌ 最复杂，容易失控

### 结论：方案B（枚举标记）为主，关键数值为辅

```json
{
  // 枚举标记：用于叙事分支
  "merchant_status": "saved",      // "saved" / "killed" / "ignored"
  "rogue_status": "spared",        // "spared" / "killed"
  "holy_dagger": "secured",        // "secured" / "taken" / "destroyed"
  
  // 数值标记：用于资源/计数（仅在必要时使用）
  "people_saved_count": 2,
  "gold_spent": 15,
  
  // 布尔标记：用于简单的开关状态
  "forest_entrance_cleared": true,
  "boss_weakened": false
}
```

## 编辑器集成方案

在事件编辑器中落地这套框架，需要扩展 JSON 数据层（不改变编辑器架构）：

### 1. Success/Failure 节点扩展：状态效果

```json
{
  "nodeId": "suc_1",
  "type": "Success",
  "data": {
    "type": "gold",
    "amount": 5,
    "text": "商人感激地给了你5金币。"
  },
  "effects": [
    {"type": "set_enum", "key": "merchant_status", "value": "saved"},
    {"type": "add_value", "key": "people_saved_count", "value": 1}
  ]
}
```

### 2. Branch 节点扩展：条件判断

```json
{
  "nodeId": "branch_1",
  "type": "Branch",
  "data": {
    "conditions": [
      {"type": "enum_is", "key": "merchant_status", "value": "saved"}
    ],
    "true_path": "opt_merchant_help",
    "false_path": "opt_no_help"
  }
}
```

### 3. 条件类型定义

| 条件类型 | 参数 | 说明 |
|----------|------|------|
| `flag_is` | key, bool | 布尔标记是否为真 |
| `enum_is` | key, value | 枚举标记是否等于指定值 |
| `value_gte` | key, number | 数值是否大于等于 |
| `value_lte` | key, number | 数值是否小于等于 |
| `has_item` | itemId | 是否持有某物品 |
