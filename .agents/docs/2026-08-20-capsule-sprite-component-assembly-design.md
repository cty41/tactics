# 胶囊角色 Sprite 混合组件拼装设计

## 目标

为无手臂、无腿的 Pure Run 胶囊角色提供通用的离线 Sprite 组件状态机，使身体、装备、远近手爪和远近脚爪可以在受控来源、固定层级和可审计审批下确定性拼装。第一落地点是修复魔剑士背向 Idle、Melee 与 Cast 中脚爪和身体的前后关系。

本设计只改变 `Tools/artworks` 离线生产与审核能力，不实现运行时换装、动态拼装或玩法逻辑。

## 已确认决策

- 第一版只支持无手臂、无腿的胶囊角色。
- 使用混合来源：身体和装备可以独立生成；手脚优先从同姿态的获批原图和语义蒙版确定性派生，确实无法得到合格组件时才允许独立生成。
- 独立生成的组件需要组件级技术检查和人工审批；确定性派生组件只需要来源、语义纯度和哈希门禁。
- 无论组件来源如何，完整 Assembly 必须重新验证并单独获得人工批准后才能晋升。
- 固定使用六层绘制顺序，不开放任意命名或任意层级图系统。

## 方案比较

### 采用：混合组件模式

身体与装备可以独立生成，手脚默认从获批完整姿态确定性拆分，只有源图缺失、粘连严重或结构错误时才升级为独立生成任务。该方案兼顾身份一致性、确定性和修复自由度。

### 未采用：所有组件完全独立生成

身体、装备、手脚全部分别调用 ImageGen。自由度最高，但容易产生描边、颜色、光照、体量和身份不一致，并显著增加审批成本。

### 未采用：只从完整图确定性拆层

继续生成完整角色，再用语义蒙版拆层重排。稳定且便宜，但无法补救原图中缺失、粘连或结构错误的手脚。

## 组件模型

每个姿态最多包含以下六个有序角色层：

1. `far_foot_overlay`
2. `far_paw_overlay`
3. `body`
4. `equipment`
5. `near_paw_overlay`
6. `near_foot_overlay`

图层顺序是状态机合同的一部分。任何组件内容、变换或顺序变化都会生成新的 Assembly 身份，并使旧的 Review 与 approval 失效。

组件种类保持为：

- `body`
- `equipment`
- `paw_overlay`
- `foot_overlay`

`paw_overlay` 与 `foot_overlay` 通过 Assembly role 区分远近侧，不增加 `near_*`、`far_*` 组件种类。

## 组件来源

### `derived`

从获批的同姿态完整图及其语义蒙版提取一个指定标签。派生记录必须绑定：

- 源 attempt 与获批状态；
- 源图和语义蒙版 SHA-256；
- `near_hand`、`far_hand`、`near_foot` 或 `far_foot` 标签；
- 确定性提取参数；
- 输出图和输出蒙版 SHA-256。

派生组件不能手工擦除错误像素。若混入身体、眼睛或装备，必须修正源语义蒙版并重新派生。

### `generated`

仅在确定性派生无法得到完整、可接触且层级正确的部件时使用。独立生成组件必须拥有普通 ImageGen 任务的 invocation、raw、prepare、feedback、retry 与审批证据，并额外绑定目标姿态、方向、近远侧、接触窗口、描边和色彩参考。

独立生成的手脚不得改变身体身份、体量或姿态；它们只负责补齐对应局部组件。

### `pre_v3_import`

只用于迁入已经明确自有且获得用户确认的旧组件。它必须保留原始哈希、处理参数、确认人、原因和时间，不伪造 ImageGen 调用记录。

## 状态与数据流

```text
姿态合同
  -> 身体 / 装备组件任务
  -> 同姿态完整图 + 语义蒙版
       -> 优先 derive 远近手脚
       -> 派生不可用时创建 generated 局部任务
  -> 各组件通过对应门禁
  -> create-assembly 固定六层与允许变换
  -> render-assembly 确定性合成
  -> 完整 Sprite validate + Review
  -> 人工批准
  -> promote
```

组件始终 `runtimeEligible: false`，不能直接 `promote`。只有 `assembled_sprite` 可以在完整验收后进入正式 Sprite 路径。

## 姿态合同

每个 Assembly 合同必须明确：

- 世界朝向、固定等距摄像机和屏幕方向；
- 哪一侧是近手、远手、近脚和远脚；
- 六层固定顺序；
- 每个部件允许出现的屏幕空间窗口；
- 部件与身体或装备的最小接触区域；
- 远侧部件允许露出的面积上限；
- 身体应遮挡的内侧边缘；
- 装备由哪只手抓握及其接触窗口；
- 允许的整数平移、等比整数百分比缩放和水平翻转。

第一版不允许旋转、非等比缩放、自由形变或像素级手工擦改。

## 组件验证

### 语义纯度

- 手爪组件只能包含对应手爪标签。
- 脚爪组件只能包含对应脚爪标签。
- 不得夹带眼睛、身体、装备、另一只手脚或特效像素。
- 输出蒙版必须与输出图尺寸和非透明区域一致。

### 接触与遮挡

- 近侧手脚必须与身体形成稳定的多像素接触面。
- 不允许浮空、透明间隙、单像素切点或细线肢体。
- 远侧手脚位于身体后层，只显示姿态合同允许的外弧。
- 身体必须遮挡远侧部件的内侧边缘。
- 远侧部件侵入核心身体区域的可见面积不得超过合同上限。

### 几何与风格

- 地面角色脚底基线保持 `y=236`，128 预览保持 `y=118`。
- 手爪必须位于姿态规定的身体侧窗口。
- 独立生成组件的颜色、描边宽度和光照方向必须匹配身体组件。
- 装备必须与指定手爪保持合同规定的多像素接触。

## Assembly 验证

- 六层顺序固定且完整，不允许重复或未知 role。
- 每个完整胶囊角色恰好拥有两只手爪和两只脚爪；被完全遮挡的远侧部件仍需在 Assembly spec 中存在。
- 身体核心逐行连续，不得因拆层产生透明裂缝、双轮廓或错误凸起。
- 身份蒙版、核心体量、脚底基线与 Tile 落点保持合同容差。
- `assemblyLayerReview` 必须同时展示单层、累积合成和最终结果。
- Tile Review 必须按真实 `64×32` 错列等距落点显示 DR/UL 对照。

## 审批规则

- 独立生成的 `body`、`equipment`、`paw_overlay` 和 `foot_overlay` 需要组件级技术验证与人工审批。
- `derived` 组件在源 attempt 已获批、语义纯度和哈希门禁通过时，不重复要求人工审批。
- `pre_v3_import` 需要明确的迁入确认 receipt。
- 组件 approval 不能替代完整 Sprite approval。
- 完整 Assembly 每次变更后都必须重新生成 Review，并由 `cty41` 单独批准。

## 失败处理

- 派生组件包含错误像素：修正源语义蒙版并重新派生。
- 源图中部件缺失、粘连或结构错误：将该部件升级为 `generated` 局部任务。
- 独立生成组件身份或风格不一致：创建新 attempt，不覆盖旧版本。
- 拼装出现裂缝、双轮廓或错误遮挡：修改组件或 Assembly spec，生成新的 Assembly 身份。
- 任一组件哈希、蒙版、变换或顺序漂移：旧 Review 和 approval 自动失效。
- 完整 Sprite 未获批准：所有组件即使分别通过也不能进入运行时。

## 第一落地点

以魔剑士三个背向姿态验证能力：

1. `idle-ul`：拆出远脚和近脚，修复两脚都完整压在身体前层的问题。
2. `melee-ul`：同时验证远脚、近脚、远手、近手与剑的六层拼装。
3. `cast-ul`：复用现有身体与脚爪组件，将当前实验性的脚爪顺序纳入正式状态机合同。

每个姿态单独完成 Review 和人工确认，不进行未确认的批量晋升。

## 自动测试

状态机测试必须覆盖：

- 合法组件种类与六个 Assembly role；
- `derived`、`generated` 和 `pre_v3_import` 的来源门禁；
- 派生操作只提取指定语义标签；
- 缺失、重复、未知或顺序错误的层被拒绝；
- 组件种类与 Assembly role 不匹配时被拒绝；
- 非法旋转、非等比缩放和非整数变换被拒绝；
- 组件、蒙版、变换和顺序哈希漂移使旧证据失效；
- 组件不能晋升，只有获批完整 Assembly 可以晋升；
- 语义污染、浮空、单像素接触、核心裂缝和远侧可见面积超限被拒绝；
- 同一输入与 spec 连续两次输出 byte-identical。

## 人工验收

- 背向姿态的远脚和远手自然位于身体后方，内侧边缘被遮挡。
- 近脚和近手位于身体前方且与主体稳定接触。
- 不出现浮空手脚、细线肢体、双轮廓、身体缺口或身份漂移。
- Idle、Melee 和 Cast 在 128 预览与真实 Tilemap 中保持相同体量、基线和朝向。
- 组件拆分不让角色呈现纸片拼贴感。

## 非目标

- 不实现运行时换装或动态组件拼装。
- 不支持有真实手臂、腿、翅膀、尾巴或多段骨骼的角色。
- 不开放任意层名、任意层数或任意绘制顺序。
- 不自动批准组件或完整 Sprite。
- 不借此修改 Godot 运行时资源、角色 Profile 或玩法代码。

## 完成标准

- 状态机能完整表达混合来源和固定六层 Assembly。
- 三个魔剑士 UL 姿态分别通过确定性生成、机器验证和完整 Review。
- 自动测试覆盖来源、层级、语义、哈希、变换与批准边界。
- 用户逐姿态确认后才允许晋升；未确认姿态保持候选或 WIP。
