# Short Term Prototype Validation Plan

## Background

- 当前问题：方向上已经收敛到“`Meowgenics` 的短局随机性 + `暗黑2` 式职业 build 和刷宝 + 一点 `英雄无敌3` 的升级选择”，但目前还停留在概念拼合阶段。真正需要验证的不是题材是否成立，而是这些乐趣来源能否在一个短局原型里形成闭环。
- 当前现状：
  - 想做的核心体验已经比较明确：搜打撤、角色 build、刷装备、短局战斗、局内随机成长、有限技能槽。
  - 职业方向已有明显倾向，可以直接借 `暗黑2` 式职业幻想起步，例如死灵法师拆为召唤、法伤、诅咒辅助等分支。
  - 也已经意识到当前战斗“远远不够”，说明单纯继续堆外围系统没有意义。
  - 现有方向存在几个明显风险：战棋容易无聊、单局可能拖长、角色可能沦为耗材、长期变成“养装备不养角色”。
- 目标：做出一个可玩的短期原型，优先验证“搜打撤 + build + 掉宝 + 撤离”能否驱动重复游玩，并找到最该继续深挖的差异化方向。
- 预期收益：
  - 尽快判断核心乐趣是不是 build 和刷宝，而不是误把重点压在完整战棋系统上。
  - 在较小内容量下验证单局时长、成长节奏、敌人差异和自动化程度的合理范围。
  - 为后续中期开发明确“先补内容”还是“先改循环”的优先级。

## Scope

### In Scope

- 搭建一个以短局为核心的战斗原型，验证单局时长、回合密度和疲劳感。
- 先做少量但分化清晰的职业/流派原型，验证 build 决策是否成立。
- 先做一小组高辨识度敌人，验证战斗是否因为敌人机制差异而持续有新鲜感。
- 搭建最小掉宝与撤离循环，验证“进入单局 -> 获得装备 -> 撤出 -> 调整配置 -> 再开一局”是否有动力。
- 验证有限技能槽与三档升级选择是否能形成稳定的局内成长体验。
- 预留并测试自动战斗或半自动战斗的减负价值，判断它应是辅助功能还是核心默认体验。

### Out of Scope

- 不在本轮原型中追求完整职业阵容、完整敌人库或大量装备池。
- 不在本轮实现完整局外建筑、长期 meta 成长或复杂经济系统。
- 不追求正式数值平衡，只做能支撑判断的体验级平衡。
- 不把重点放在大地图、叙事包装、美术完成度或长期运营结构。
- 不急着证明“完整战棋框架”是否先进，优先证明核心循环是否值得继续。

## Tasks

### Task 1: 明确原型的核心循环与失败标准

- 目标：把短期原型要验证的核心问题写清楚，避免原型阶段继续扩 scope。
- 输入：现有方向共识，包括搜打撤、角色 build、刷装备、短局随机战斗、有限技能槽、三档升级。
- 输出：一份原型判定标准，明确什么算“值得继续做”，什么算“需要转向”。
- 验收标准：
  - 明确记录本轮原型只验证“核心循环成立性”，而不是完成所有系统。
  - 至少定义 3 个成功信号，例如“玩家愿意连续开 3 局”“不同 build 带来明显不同打法”“掉落会影响下一局配置”。
  - 至少定义 3 个失败信号，例如“局内决策重复”“角色与装备成长关系失衡”“单局太长导致疲劳”。

### Task 2: 做一个可反复测试的短局战斗切片

- 目标：验证战斗本身是否足够支撑短局反复游玩，而不是只在纸面上成立。
- 输入：当前战斗基础，以及“战棋容易无聊、需要短局化”的已知判断。
- 输出：一个可在较短时间内完成的战斗切片，支持重复开局与快速复盘。
- 验收标准：
  - 单局时长被控制在一个可反复测试的范围内。
  - 每局内存在稳定的决策密度，而不是大量低价值移动或等待。
  - 能通过连续体验快速判断战斗是否拖沓、是否容易腻。

### Task 3: 做职业幻想明确的最小 build 原型

- 目标：验证“角色 build”是不是比“单纯战棋招式”更能驱动乐趣。
- 输入：职业先参考 `暗黑2` 的方向；有限技能槽；三档升级选择。
- 输出：2 到 3 个职业或同一职业的 2 到 3 个分支原型，要求差异一眼可见。
- 验收标准：
  - 每个原型都能被一句话概括玩法核心，例如“召唤堆场面”“法伤清群”“诅咒控场”。
  - 有限技能槽会迫使玩家取舍，而不是全都带上。
  - 升级三档选择会改变打法方向，而不是只加数值。

### Task 4: 做一组能拉开体验差异的敌人原型

- 目标：验证敌人机制差异是否足以支撑重复游玩，避免战棋因敌人同质化而变无聊。
- 输入：`Meowgenics` 给出的启发，即“有趣很大程度来自能力和敌人的组合变化”。
- 输出：3 到 5 个高辨识度敌人原型，每个敌人都代表一种战斗压力。
- 验收标准：
  - 敌人之间的威胁来源明显不同，例如突进、召唤、范围压制、诅咒干扰等。
  - 同一套角色配置面对不同敌人时，会自然调整打法。
  - 不依赖大量数量堆叠，也能感受到战斗变化。

### Task 5: 做最小掉宝与撤离闭环

- 目标：验证“搜打撤 + 刷装备”是不是这个项目真正的驱动力。
- 输入：项目方向中的搜打撤设定，以及“可能变成养装备不养角色”的风险。
- 输出：一个最小可用的掉落、携出、局外调整、再入局流程。
- 验收标准：
  - 玩家在局内获得的装备能明确影响下一局配置。
  - 撤离是一个有策略意义的决定，而不只是结束按钮。
  - 能观察到角色成长与装备成长的关系，没有完全滑向“角色只是耗材”。

### Task 6: 验证自动战斗或半自动战斗是否需要提前进入核心体验

- 目标：评估战棋减负方案是否应该尽早进入产品核心，而不是留到后期补。
- 输入：关于 `Meowgenics` 短局体验与 `英雄无敌3` 自动战斗习惯的讨论结论。
- 输出：一版自动战斗或半自动战斗验证方案，用于比较手动与自动体验差异。
- 验收标准：
  - 能明确比较“纯手动”和“自动/半自动”在疲劳感、可读性、构筑乐趣上的差异。
  - 若自动化更优，能说明玩家的主要乐趣应更偏 build 和战前配置。
  - 若自动化更差，能说明哪些关键决策必须保留给玩家手动操作。

### Task 7: 组织小规模连续试玩并收敛结论

- 目标：用连续多局试玩来判断核心循环是否真的成立，而不是凭单局印象决策。
- 输入：前述战斗、build、敌人、掉宝、撤离、自动化原型。
- 输出：一份短期原型测试结论，明确下一阶段最该优先补的方向。
- 验收标准：
  - 至少能基于连续多局体验输出结论，而不是单次试玩主观感受。
  - 能明确判断下一阶段更该补“内容量”“build 深度”“掉宝系统”还是“战斗减负”。
  - 能给出一个继续推进的主方向，以及至少一个应暂缓的方向。

## Risks & Open Questions

- 如果单局不够短，战棋疲劳感会掩盖 build 与掉宝本身的乐趣，导致判断失真。
- 如果装备收益过强、角色成长过弱，系统会滑向“养装备不养角色”。
- 如果敌人差异不足，原型很可能会错误地把问题归因到战斗系统本身。
- 如果 build 分支不够清晰，玩家会觉得只是换皮技能，而不是在做真正构筑。
- 自动战斗是否应该成为核心体验的一部分，目前仍是需要重点验证的问题，而不是默认附属功能。

## Assumptions

- 默认本轮原型以“验证核心循环”为先，不追求完整产品结构。
- 默认职业与技能设计可以先借鉴 `暗黑2` 和 `Meowgenics` 的成熟表达，再在原型阶段寻找差异化。
- 默认“短局、多次重复测试”比“长局、单次深度体验”更适合当前验证阶段。
- 默认本轮允许使用占位内容和简化系统，只要不影响对核心乐趣的判断。
