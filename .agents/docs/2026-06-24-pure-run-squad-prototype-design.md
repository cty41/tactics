## 一句话定位

这是一个以 `固定三人小队` 为核心单位、以 `FTL 式自由星图` 为推进结构、以 `职业分支 + 技能 + 装备 + 消耗品` 为 run 内成长源的战棋构筑原型。

它不验证带出收益，不验证局外成长，而是验证：玩家是否愿意在一局结束后，立刻再开一局尝试另一种三人协同构筑。

## 核心设计决策

### 1. 不把成长带到局外

- run 结束后，主成长清空
- 不存在装备带出
- 不存在撤离收益
- 不存在跨局积累的主成长线

局外层最多只保留轻量解锁空间，但不应成为原型阶段的重点。

### 2. 保留 FTL 式自由星图

- 地图仍然采用可探索的星图结构
- 重点保留路径选择、信息不完全和推进顺序判断
- 但星图的价值从“如何把收益带出去”改成“如何为本局三人小队找到更合适的成长路径”

这意味着它不是线性爬塔，也不是纯菜单跳点，而是保留探索感的 run 内构筑地图。

### 3. 保留固定三人小队

- 每个 run 开始时确定 3 名角色
- 单个 run 内不换人、不招募替补
- 整个 run 的构筑核心是三人分工、技能协同、装备分配和资源调度

这条决策非常关键。它把产品从“单角色构筑游戏”拉向了“战术小队构筑游戏”。

## 成长结构

本原型采用三层成长源，分别承担不同职责。

### 职业分支：定义成长骨架

- 每个角色都有明确职业身份
- 每个职业至少有 2-3 条可辨识的分支方向
- 职业分支决定该角色更适合承担什么职责

职业分支的作用不是单纯加数值，而是回答：

1. 这个角色在小队里负责什么
2. 这个职业自己玩起来爽在哪
3. 他的技能池偏向什么
4. 他与队友能形成哪些特殊组合乐趣
5. 装备优先级会偏向什么

### 技能：定义战斗联动

- 技能是角色在战斗中的主要表达层
- 技能成长应改变操作顺序、目标选择、站位偏好或队友配合
- 技能不是独立系统，而必须和职业分支与装备形成联动

技能的设计目标不是“角色各玩各的”，而是让玩家产生类似这样的思考：

- 先由 A 上 debuff，再让 B 收割
- C 负责保护或补位，让 A/B 能继续滚起来

### 装备槽：定义角色配置

- 不使用“遗物”模型
- 使用传统装备槽表达成长
- 装备应明显影响角色职责，而不是只替换更高数字

装备的意义在于：

1. 让掉落具有“给谁穿”的决策价值
2. 让同一个职业分支在不同 run 中产生不同构筑手感
3. 让小队内部出现资源分配冲突

### 消耗品槽：定义资源调度

- 消耗品是 run 内资源管理的重要组成部分
- 它既服务战斗，也服务星图推进
- 消耗品不应只是回血瓶，还应承担临时补强、解局和容错的作用

消耗品的存在，是为了让玩家在“继续推进”和“保守保命”之间做更细的判断。

## 首个真实 Run 的预设三职业规格 v1

首个真实 run 不做开局选人，而是使用 `固定预设三职业`。目的不是提前锁死最终职业阵容，而是先用一套受控实验组验证三件事：

1. 职业本身是否各自成立且好玩
2. 三人之间是否存在清晰但不僵硬的职责结构
3. run 内资源是否会根据敌人、掉落和当前压力在三人之间动态偏移

### 职业 1：死灵法师

#### 职业爽点

- 操控亡灵在前线顶住压力
- 通过诅咒削弱敌人，用较低的正面暴露去遥控战斗
- 具备明显的“一人成军”倾向

#### 队伍职责

- 默认的前场制造者
- 通过召唤物承担主要承压骨架
- 通过诅咒制造削弱、路径干扰和阵型约束

#### 组合特征

- 对他人依赖最低，是三职业中最能独立运转的角色
- 其真正价值不在于独自终结战斗，而在于为队友创造更适合输出和几何兑现的局面

#### 关键限制

- 召唤物数量不是主要问题，真正限制是 `召唤物质量有限`
- 召唤物足以构成前场骨架，但不足以单独稳定解决前线压力
- 这保证死灵法师不会强到把另外两个职业变成附属挂件

### 职业 2：法师

#### 职业爽点

- 范围爆发
- 火系魔法负责高伤害 AOE 清场
- 冰系魔法负责中等伤害 AOE 并施加寒冷 buff，形成持续减速与控场

#### 队伍职责

- 队伍中的 `清场核心`
- 同时具备控场价值，但本体 build 的重点是 `火法清场 / 冰法控场` 的模式切换

#### 组合特征

- 与亚马逊不是上下位关系，而是 `双核并存`
- 法师负责解决密集敌群、散怪清理和行动效率压制
- 当敌人不适合穿线时，法师应成为更自然的场面接管者

#### 关键限制

- `脆，怕贴脸`
- 一旦被近身，法师的清场与控场价值会迅速下降
- 因此法师需要死灵的前场骨架与全队的站位保护来稳定兑现价值

### 职业 3：亚马逊女战士

#### 职业身份

- `近战几何型主核，远程投掷型副核`
- 武器设定为 `持盾 + 长矛/标枪`
- 战斗气质是 `敏捷格挡型中前场`，不是传统重装前排

#### 职业爽点

- 最核心的手感不是捡回标枪，也不是单纯高伤，而是 `站在正确位置，让近战十字穿透攻击吃到整条有效线`
- 近战模式才是她最主要的高光兑现方式
- 投掷模式提供更高单体伤害，但不承担主几何高光

#### 第一主决策

- `这一枪现在该近战打，还是投掷出去`

这个决策不是风格切换，而是价值切换：

- 近战：主打几何兑现、穿线、多段打击与局部控位
- 投掷：主打单体高伤、远端关键目标处理和安全输出

#### 近战价值

- 近战武器具备 `三格十字穿透攻击`，这是她最具辨识度的主高光
- 近战技能应围绕 `多段打击 + 穿透覆盖 + 控位辅助` 展开
- 她的代表性回合不是贴身处决一个目标，而是 `用近战吃到整条有效攻击线`

#### 投掷价值

- 投掷只打一个单位，但伤害比近战更高
- 投掷主要用于：
  - 打远端关键目标
  - 在不适合贴身时保持威胁
  - 作为近战几何之外的副核输出模式

#### 回收机制的定位

- 标枪投出后需要回收，这一设定保留
- 但它的定位是 `风味 + 平衡限制`，而不是职业成立根基
- 换言之，去掉“捡枪”的麻烦后，这个职业仍然成立；真正支撑她的，是近战几何和双态切换

#### 关键限制

- 她最怕的不是贴脸，而是 `敌人站得太散`
- 一旦敌人无法形成有效线，她的近战主高光就很难兑现
- 因此她不是任何局面都稳定强，而是一个明显吃阵型条件的主核

#### 主配合对象

- 她最希望配合的不是法师，而是 `死灵法师`
- 原因不是吃 buff，而是死灵法师的召唤物与诅咒更容易把敌人挤成适合穿线的结构

### 三职业之间的结构关系

#### 默认前场结构

- 默认前场承压者是 `召唤物`
- 亚马逊不是传统意义上的主坦，她更像 `借前场打高光的人`
- 法师则明确站在后场，靠空间安全兑现清场价值

#### 主配合链

- `死灵法师 -> 亚马逊` 是首条最明确的主配合链
- 死灵法师负责把敌人限制到更适合穿线的位置
- 亚马逊负责将这种位置优势转化为近战几何收益

#### 双核关系

- `法师` 与 `亚马逊` 是双核并存，不是辅助关系
- 两者的区别不在于谁伤害更高，而在于谁吃的场面条件不同：
  - 法师吃 `范围密度`
  - 亚马逊吃 `线性几何`

#### 团队级天敌

- 这支队伍最怕的不是纯正面硬碰，而是 `远程分散火力队`
- 原因：
  - 召唤物难以有效卡住整片场面
  - 亚马逊难以吃到有效穿线
  - 法师的 AOE 覆盖价值被稀释，且自身又怕持续远程消耗

#### 资源倾斜原则

- 这支队伍没有固定唯一主 C
- run 内资源应根据 `敌人类型 + 掉落结果 + 当前节点压力` 动态偏移
- 资源倾斜逻辑示例：
  - 更适合铺场与阵型限制的战斗：偏死灵法师
  - 更适合穿线兑现、关键单体处理的战斗：偏亚马逊
  - 更适合大范围清场、散怪处理与控场切模式的战斗：偏法师

这条原则是 pure run 重开价值的重要来源之一：同一套三职业，因敌人、地图和掉落不同，可以在不同局里形成不同的主核重心。

## 技能层讨论沉淀 v0

以下内容用于保留当前已经完成的技能层讨论结果。它们代表“首轮实现前已确认的技能方向”，不等同于最终完整职业树。

### 当前方法调整

- 目前已经确认：如果继续逐个技能直接细化到所有实现参数，会出现从下往上的倒置风险。
- 因此当前技能层讨论只保留两类内容：
  1. 已经足够稳定、值得留档的技能定义
  2. 明确列出的 TODO，等待中上层 build 框架确定后再回填

### 法师：首轮技能包（已明确）

法师首轮技能包的目标，不是把完整法术库做完，而是用最少的一组技能验证三件事：

1. 火 / 冰双模式是否成立
2. 法师是否真的是清场核心而非纯炮台
3. 脆、怕贴脸这一弱点是否通过位移技能变成可操作问题，而不是纯处罚

#### 已确定的技能清单

- 基础单体法术：`火球术`
- 基础单体法术：`寒冰箭`
- 高阶 AOE 法术：`陨石术`
- 高阶 AOE 法术：`暴风雪`
- 位移 / 保命技能：`瞬移术`

这 5 个技能在首轮中的职责分工为：

- `火球术` / `寒冰箭`：提供稳定的单体输出与基础模式表达
- `陨石术` / `暴风雪`：提供火法清场与冰法控场的高阶兑现手段
- `瞬移术`：体现法师脆、怕贴脸时的操作空间

#### 火球术（已细化到实现参数）

##### 技能定义

- 目标类型：指定目标发射
- 技能形状：`单体命中 + 小爆炸`
- 爆炸范围：`命中点所在十字 1 格`
- 施法距离：`5 格`
- 视线规则：`需要视线`
- 友伤规则：`不伤友军`

##### Projectile 规则

- 以 `projectile` 形式直线飞行
- `只有敌方单位阻挡`
- 碰到路径上第一个敌方单位即爆炸
- 爆炸位置以实际命中点为准，不保证一定命中原指定目标

##### 效果定义

- 主命中单位：`极高伤害`
- 十字溅射单位：`很低伤害`
- 附加效果：
  - `破冰`
  - `点燃`

##### 资源规则

- 冷却：`无冷却`
- 法力消耗：`低消耗`

##### 功能完成度验收

1. 只能在 `5 格 + 视线内` 合法施放
2. 火球会沿直线飞行，不是瞬发
3. 友军和己方召唤物不会拦截火球
4. 第一个敌方阻挡单位会吃到主命中并触发爆炸
5. 爆炸会正确作用于命中点十字 1 格
6. 不会误伤友军
7. 主命中高伤、溅射低伤结算正确
8. 对冰冻目标能正确破冰
9. 点燃会正确施加到命中的合法敌方单位
10. 技能释放后只扣低法力，不进入冷却
11. 预览与实际命中结果一致

##### 技能定义

- 技能形状：`直线 projectile 单体命中`

- `基础冰魔法`：只负责发放寒冰箭，不强化它
- `高级冰魔法`：降低 `寒冰箭` 的 MP 消耗
- `大师冰魔法`：寒冰箭命中后有概率 `反弹` 至附近 `3 格` 内的 `其他单位`，反弹伤害减半

##### 功能完成度验收

1. 能正确指定目标并发射直线 projectile
2. projectile 会被路径上第一个敌方单位拦下并结算
3. 命中后正确造成单体伤害
4. 命中后正确施加冰冻减速 debuff
5. 技能不会继续穿透命中后续目标
6. 高级冰魔法生效后，寒冰箭 MP 消耗正确降低
7. 大师冰魔法生效后，寒冰箭命中后会按概率检查反弹
8. 反弹目标只在命中点附近 `3 格` 范围内选取
9. 反弹伤害正确按减半结算
10. 预览、飞行表现、命中反馈与实际结算一致

#### 霹雳闪电（已细化到实现参数）

##### 技能定义

- 目标类型：指定单位
- 技能形状：`单体直接命中`
- 施法距离：待后续补数值
- 视线规则：`不受视觉阻挡影响`
- 友伤规则：待后续确认，当前默认不伤友军

##### 命中规则

- 直接对目标单位生效
- 不使用 projectile
- 不存在弹道或飞行过程
- 不受中间单位阻挡

##### 效果定义

- 对目标单位造成伤害
- `基础电魔法`：只负责发放霹雳闪电，不强化它
- `高级电魔法`：为霹雳闪电增加 `小概率眩晕`
- `大师电魔法`：进一步提高 `眩晕概率`

##### 功能完成度验收

1. 能正确指定合法目标并即时生效
2. 技能不生成 projectile，不走飞行过程
3. 中间单位不会阻挡霹雳闪电命中目标
4. 目标单位会正确承受单体伤害
5. 高级电魔法生效后，霹雳闪电会按设定小概率施加眩晕
6. 大师电魔法生效后，眩晕概率会正确提高
7. 非法目标选择会被正确拦截
8. 技能预览、即时命中反馈与实际结算一致

#### 瞬移术（已细化到实现参数）

##### 技能定义

- 目标类型：指定地块
- 技能形状：`瞬时位移`
- 施法范围：`视觉可见范围内` 且在技能允许的最大距离内
- 友伤规则：无

##### 位移规则

- 角色瞬间移动到指定位置
- 不使用 projectile
- 基础形态要求目标地块 `视觉可见`
- 必须在技能允许的位移距离内

##### 与专长阶段的关系

- `高级电魔法`：瞬移术进入技能候选池
- `大师电魔法`：
  - 降低瞬移术魔法消耗
  - 允许瞬移术 `无视视觉可见性`

##### 功能完成度验收

1. 能正确选择合法地块作为位移终点
2. 超出技能距离的地块会被正确拦截
3. 基础形态下，不可见地块无法被选择
4. 位移后角色正确出现在指定位置
5. 位移不生成弹道或飞行过程
6. 大师电魔法生效后，瞬移术法力消耗正确降低
7. 大师电魔法生效后，不可见但合法的终点可被选择
8. 预览、合法落点显示与实际位移结果一致

## 亚马逊分支骨架 v1

### 参考来源（Mew）

亚马逊的三条技能分支不直接照搬 `Mew` 里的某个职业，而是综合借用近战职业的几类能力表达：

1. `Fighter`
   - `Dash`：冲脸开团、近战位移压迫
   - `Spin`：多段近战、范围命中
   - `ThunderPunch`：单点控制与元素打断
2. `Butcher`
   - `HogRush`：带位移和路径压迫的近战动作
   - `Burp`：击退 / 逼位
   - `Mutilate`：多段或重近战伤害表达

这些参考帮助亚马逊在“近战几何主核、远程投掷副核、敏捷格挡型中前场”的前提下形成三条技能分支。

### 总规则

- 亚马逊与法师、死灵法师一样，至少拥有 `3 条技能分支`
- 开局从 3 条基础分支中随机获得 1 条
- 同时自动获得对应的基础技能
- `基础阶段` 只负责发放基础技能并确定分支起点
- `高级阶段` 打开功能技能候选
- `大师阶段` 打开终局技能候选并强化整条线已有技能

### 分支 1：长矛专长

定位：

- 亚马逊最核心的近战几何主线
- 以 `直线穿透`、`多段压线`、`移动后伤害兑现` 为主
- 是最能体现“站位对了，一枪吃整条线”的高光分支

#### 长矛分支·基础阶段

- 基础技能：`突刺`
- 技能效果：对前方直线上的 `2 个敌人` 造成伤害

#### 长矛分支·高级阶段

- 功能技能候选：`连续刺击`
- 技能定位：在一定范围内可以选择多个目标的多段攻击技能
- 专长强化：
  - `突刺` 可对前方直线上的 `3 个敌人` 造成伤害
  - `连续刺击` 获得后，作为长矛线的多目标多段表达

#### 长矛分支·大师阶段

- 终局技能候选：`三连刺`
- 技能定位：扇形攻击区域的 AOE，高伤害，高消耗
- 专长强化：
  - `突刺` 根据亚马逊在攻击前移动的格数提高伤害
  - 攻击结算后，该移动计数重置
  - `连续刺击` 在大师阶段额外增加 `1 段攻击`
  - `三连刺` 作为长矛线的终局范围爆发技

### 分支 2：投枪猎杀

定位：

- 远程投掷副核主线
- 以 `单体高伤`、`关键目标处理`、`标枪回收节奏` 为主
- 用来弥补亚马逊在敌人分散、无法近战吃线时的解题能力

#### 投枪分支·基础阶段

- 基础技能：`毒矛`
- 技能效果：远程直线投射物，碰撞到单位后造成伤害并施加 `中毒 debuff`

#### 投枪分支·高级阶段

- 功能技能候选：`回收长矛`
- 技能定位：在一定范围内直接回收长矛
- 专长强化：
  - `毒矛` 可穿透 `1 个敌人`
  - 让投枪线从“单次投射”推进到“可持续远程压制”

#### 投枪分支·大师阶段

- 终局技能候选：`雷神之怒`
- 技能定位：丢出的长矛化身闪电，击中第一个单位后分裂继续发射（分裂方向和数量待定）
- 专长强化：
  - `回收长矛` 提升为 `全地图范围`
  - `毒矛` 在最后命中的敌人处产生 `毒雾`
  - `毒雾` 范围内敌人获得 `中毒 debuff`
  - `毒雾` 持续 `2 回合`

### 分支 3：被动与魔法专长

定位：

- 非直接武器主输出线
- 通过被动、分身、变身等手段补足亚马逊的生存、节奏与爆发窗口
- 不与长矛 / 投枪直接抢主输出身份，但决定她能否稳定活到高光回合

#### 被动与魔法分支·基础阶段

- 基础技能：`战斗技巧`
- 技能定位：被动技能
- 技能效果：增加 `30% 闪避率`

#### 被动与魔法分支·高级阶段

- 功能技能候选：`分身`
- 技能定位：在自己的位置产生一个 `50% HP` 的分身吸引原先敌人的攻击，自己后撤到旁边合法格
- 专长强化：
  - `战斗技巧` 额外获得：普通近战攻击后 `30%` 概率立刻再触发一次近战攻击（仅限一次）

#### 被动与魔法分支·大师阶段

- 终局技能候选：`变身女武神`
- 技能定位：生命值提高 `40%`，攻击提高 `40%`，持续 `5 回合`
- 专长强化：
  - `战斗技巧` 额外获得 `20% 暴击率提升`
  - `分身` 升级后会清除自身 `debuff`

### 三分支的关系

- `长矛专长`：主高光线，定义亚马逊的近战几何身份
- `投枪猎杀`：单体副核线，解决远端关键目标和分散敌人问题
- `被动与魔法专长`：生存与爆发辅助线，保证她在危险距离中还能继续兑现前两条输出线

- `毒矛`、`回收长矛`、`雷神之怒` 的具体实现参数
- `战斗技巧`、`分身`、`变身女武神` 的功能完成度验收与边界条件
- 长矛分支中 `突刺` 的距离、命中判定与伤害公式细节

4. 技能增强是数值强化还是形态分叉

## 中上层 Build 框架 v2（纯技能树版本）

以下内容用于约束三职业在 pure run 中的成长方式。当前版本已不再使用独立的“专长系统”，而是将职业方向、阶段推进与候选过滤统一收束到 `技能树 + 属性门槛 + 前置技能`。

### 升级包结构

每次升级固定发放：

1. `+1 属性点`
2. `技能三选一`

技能候选的默认结构为：

- `2 个职业技能候选`
- `1 个通用候选`

若当前职业技能池在本次前置与属性门槛过滤后不足 `2 个`，则由 `通用候选` 补位，直到补满 `3 选 1`。

这里的“通用候选”可以是：

- `通用主动技能`
- `通用被动技能`

### 升级结算顺序

每次角色升级时，结算顺序固定为：

1. `自动升级提示`
2. `属性加点`
3. `技能三选一`

说明：

- 自动升级提示只负责展示已获得特殊技能因技能树阶段推进而产生的升级结果
- 属性加点发生在技能候选之前，意味着本次加点会直接影响当前这次升级里的技能主属性门槛判定
- 不再存在独立的“专长二选一”步骤，build 身份由技能前置链本身承担

### 升级 UI 最小交互稿

第一版仍采用 `单个升级面板 + 分步区块推进`，但区块收缩为三段：

1. `自动升级提示区`
2. `属性加点区`
3. `技能三选一区`

#### 自动升级提示区

- 若本次升级没有触发自动升级，该区块折叠或显示“无自动升级”
- 若触发了自动升级：
  - 展示技能名
  - 展示升级前 -> 升级后
  - 使用纯展示卡片，不提供选择
- 玩家阅读后即可继续，不需要单独确认

#### 属性加点区

- 先展示当前属性点数量（第一版默认每次升级 `+1`）
- 展示 7 维属性当前值
- 玩家必须先分配完当前属性点，技能区才解锁
- 分配后立即刷新技能候选门槛是否满足

#### 技能三选一区

- 属性点分配完成后解锁
- 展示 3 张技能候选卡
- 每张卡至少显示：
  - 技能名
  - 所属职业 / 分支 / 通用来源
  - 基础 / 高级 / 大师技能类型
  - 技能一句话说明
  - 若该技能后续存在升级链，标记“可进阶”
- 若当前阶段没有可用职业技能：
  - 由通用候选补位
  - 仍然保持 `3 选 1`

#### 确认按钮的启用条件

- 自动升级提示区不影响确认状态
- 必须满足以下条件后，确认按钮才可点击：
  - 属性点已分配完成
  - 技能区已选择 1 项
- 若本次升级只有自动升级而没有新的候选技能，则允许直接确认

### 属性规则

- 保留现有 `7 维属性` 与 `中性值 5`
- `Strength / Agility` 的旧规则只保留给：
  - 近战普通攻击
  - 远程普通攻击
  - 少数基础物理动作
- 所有技能不再吃全局“近战 / 远程”规则
- 每个技能只绑定 `一个主属性`
- 技能数值公式：`基础值 + 主属性 × 系数`
- 属性只影响 `数值强度`
- 属性不改变：
  - 范围
  - 形状
  - 距离
  - 命中数
  - projectile 行为

### 技能树规则

- 每个职业至少拥有 `3 条技能分支`
- 每条分支都以 `基础技能 -> 高级技能 -> 大师技能` 串联
- 所有职业的首轮入场规则统一：`从该职业的基础技能分支中随机选择 1 条，并自动获得对应基础技能`
- build 身份由技能前置链本身承担，不再通过独立专长对象表达

### 技能升级规则

- 技能默认只有“已获得 / 未获得”两种状态
- 但对需要成长层次的职业分支技能，允许轻量级升级：
  - `基础技能`：可升级 2 次
  - `高级技能`：可升级 1 次
  - `大师技能`：不可升级
- 这些升级版仍然作为技能候选参与 `技能三选一`
- 也就是说：
  - 新技能获取
  - 旧技能升级版
  - 通用主动 / 被动技能
  都可能进入同一轮技能候选

### 技能候选生成规则（当前已定）

- 采用 `固定池抽取`
- 候选优先来自当前职业技能池
- 默认结构：`2 个职业技能候选 + 1 个通用候选`
- 若职业技能候选不足 `2 个`，则由通用候选补位
- 过滤条件：
  - 满足 `前置技能`
  - 满足 `主属性值限制`

### 技能升级版候选规则

- 技能升级版候选与“新技能候选”在 `职业技能池` 内 `完全平权随机`
- 若同一轮同时满足多个升级版，它们与其他合法职业技能候选一起进入同一抽取池，不做额外优先级区分
- 若某技能链已有更高阶新技能与旧技能升级版同时满足条件，两者也按同等权重参与职业技能候选抽取
- 同一个技能的升级版允许在后续升级中再次出现，只要：
  - 该技能仍有更高升级版可选
  - 当前角色属性仍满足对应门槛

### 技能阶段门槛规则

- `高级技能` 与 `大师技能` 不只看前置，还要看 `技能主属性` 是否达到门槛
- 门槛使用 `角色基础属性值` 判断
- 不计入：
  - 装备加成
  - 临时 buff
  - 其他战斗内短时增益

统一阶段门槛：

- `基础技能`：主属性达到 `5`
- `高级技能`：主属性达到 `7`
- `大师技能`：主属性达到 `9`

### 与升级节奏的联动

- 当前额外确认一条高层规则：`每场战斗后只有一个角色可以升级`
- 每次升级只给 `+1 属性点`
- 当前不再额外限制“每张地图最多升级几次”
- `谁升级` 的判定规则为：
  - 每次战斗胜利后，优先让 `当前等级最低的角色` 升级
  - 若存在多个同为最低等级的角色，则在这些角色中 `随机选择 1 个` 升级

这意味着专长推进速度的主要限制，来自：

1. 升级名额稀缺
2. 专长主属性门槛
3. 技能 / 专长候选池的前置过滤

这条规则带来的结果是：

- 单个角色进入高级 / 大师技能阶段不会过快
- 队伍内三人不容易同时高速冲到各自分支的高阶阶段
- 在正常三人都存活的情况下，要把角色推进到大师技能阶段本身就需要较多战斗与较多属性投入，不需要再用地图升级次数做硬限制
- 若队伍出现减员，剩余角色更快进入大师技能阶段，反而可以作为对减员损失的自然补偿

这条规则的设计价值在于：

- 不靠纯随机稀释，也不靠“每图固定升级上限”来限制高阶专长
- 而是通过 `升级机会稀缺 + 属性门槛 + 前置过滤` 来控制 build 推进速度
- 同时强化“本局资源倾斜给谁”这一 pure run 核心判断

### 通用候选的属性门槛规则

- `通用候选` 同样需要属性门槛，不走“只有前置、没有属性要求”的路线
- 但通用候选的门槛不按单个候选逐个随意指定，而是 `按类别统一绑定属性`

这意味着通用候选后续在设计时，应先定义类别，再统一定义对应的主属性门槛。示意例如：

- 生存类通用被动 -> 体质
- 暴击 / 赌运类通用被动 -> 幸运
- 法力 / 施法效率类通用被动 -> 魅力
- 通用主动技能 -> 按技能自身主属性定义

采用这种规则的原因是：

1. 保持职业技能分支与通用候选的门槛体系一致
2. 避免通用候选因为门槛松散而反客为主
3. 让玩家更容易理解“我堆这个属性，会更容易进入哪类通用候选池”

这表示职业技能分支仍是 build 主轴，而通用候选作为跨职业变化源进入同一个抽取体系，但不再享有单独权重修正。

### 待继续收敛的规则

以下仍需继续 grill 后定稿：

1. 拿到某条基础技能分支后，后续更高阶段同分支技能是否提升抽取权重
2. 已选主分支是否应获得保底候选，避免成长方向漂移
3. 通用专长允许承担到什么程度的功能：纯强化、通用技能，还是两者兼有

## 通用被动候选池 v1

本节明确：当前讨论的“通用被动候选”优先参考 `Mewgenics` 的 `colorless_passives.gon`，而不是 `colorless_abilities.gon`。也就是说，本轮优先参考的是跨职业被动能力，而不是通用主动技能。

### 当前采用的通用被动大类

- `生存类`
- `资源类`
- `暴击 / 机会类`

说明：

- `机动类` 暂不纳入首轮通用被动池，避免与法师的瞬移术、未来野蛮人的跳跃等职业标志技能冲突。
- `协同强化类` 暂不纳入首轮通用被动池，避免抢占职业技能分支本应承担的队伍关系设计。
- `独狼天赋` 保留为 TODO，视为规则改写型专长，后续单独设计，不进入首轮普通通用池。

### 生存类通用被动

#### 1. 自然愈合

参考倾向：`NaturalHealing` / `HealthRegenUp`

属性类别：`体质`

定位：

- 稳定续航
- 降低连续战斗的磨损压力
- 不参与爆发，只改善长线推进容错

阶段效果：

- `基础`：战斗结束后增加 HP 和 MP 回复量
- `高级`：每回合结束后增加 HP 和 MP 回复量
- `大师`：同时增加战斗后与每回合结束时的回复量数值

说明：

- 该项当前作为 pure run 连战节奏的核心生存向通用被动之一
- 它服务的是“能不能继续推进”，不是“单场能不能翻盘”

#### 2. DeathProof 型专长（名称待定）

参考倾向：`DeathProof` / `ChanceToRevive`

属性类别：`体质`

定位：

- 一次性保命
- 提供高光容错
- 不应成为稳定收益来源

阶段效果：

- `基础`：每场战斗仅限一次，濒死时保留 1 HP
- `高级`：同样每场战斗仅限一次；触发后获得一个 `1 回合伤害护盾`（待实现）
- `大师`：同样每场战斗仅限一次；触发后获得一个 `1 回合圣盾`（无敌）

说明：

- 当前已明确三个阶段都必须保留“仅限一次”的硬限制
- 这是为避免其变成泛用最优生存解

### 资源类通用被动

#### 3. 资源效率专长（名称待定）

参考倾向：`Study` / `Unrestricted` / `Brainstorm` 的被动化理解

属性类别：`魅力`

定位：

- 改善施法和技能循环压力
- 为法师和死灵法师提供更稳定的技能经济

说明：

- 当前只保留类别与定位
- 具体阶段效果仍待后续补完

阶段效果：

- `基础`：技能法力消耗小幅降低
- `高级`：技能法力消耗进一步降低
- `大师`：每回合首次施法固定返还少量法力

说明：

- 大师阶段当前明确采用 `固定返还`，不是按技能消耗比例返还
- 这样更容易控制强度，也更容易让玩家预估回合内资源节奏

#### 4. 战后资源 / 掉落专长（名称待定）

参考倾向：`MetalDetector`

属性类别：`幸运`

定位：

- 改善本局运营资源
- 提高战斗外资源收益

说明：

- 该类偏 run 层，不是首轮最优先的战斗表达专长
- 可保留为次优先级的通用资源向选择

#### 4. 收割回复

参考倾向：`KillsHeal` / `SoulReap` 的击杀回收思路

属性类别：`幸运`

定位：

- 奖励击杀
- 把“打顺了”转化为更稳定的连续推进能力
- 同时连接战斗内收益与战后续航节奏

阶段效果：

- `基础`：击杀后只恢复少量 HP
- `高级`：击杀后恢复更多 HP，并少量恢复 MP
- `大师`：击杀后恢复进一步提升，并获得一个短时小增益

说明：

- 基础版当前已明确不恢复 MP，只恢复 HP
- 这样可以避免它在首轮过早变成法系和物理系都无脑通吃的万能资源专长

### 暴击 / 机会类通用被动

#### 5. 幸运汲取

参考倾向：`LuckDrain`、部分 `SelfAssured` 的成长思路

属性类别：`幸运`

定位：

- 将战斗中的击杀与暴击节奏转化为幸运成长
- 让幸运流成为一种明确但不稳定、但可逐步蓄势的成长方向

阶段效果：

- `基础`：自己击杀单位时，获得 1 层 `幸运增益`
- `高级`：任意敌方单位死亡时，获得 1 层 `幸运增益`
- `大师`：每累计 3 层 `幸运增益`，获得一个 `下次攻击必定暴击` 的 buff；暴击后该 buff 消失，幸运计数重置

说明：

- `幸运增益` 的具体数值效果待后续细化，但当前定位已明确为幸运向的可堆叠成长资源
- 大师阶段的核心不是永久提升，而是把幸运积累转化为一次确定性的暴击兑现窗口

#### 6. 过度自信

参考倾向：`OverConfident`

属性类别：`幸运`

定位：

- 在理想状态下提供高收益
- 通过“未受伤”这一条件制造高风险高回报的机会流

阶段效果：

- `基础`：获得暴击率提升
- `高级`：只要在一场战斗内 `没受伤`，该效果就持续激活
- `大师`：效果失效后，如果连续 `3 回合没受伤`，还能重新激活

说明：

- 与 `幸运汲取` 不同，`过度自信` 不依赖击杀滚雪球，而依赖角色是否能维持完美状态
- 该专长更适合法师或偏谨慎站位的高风险玩法，不适合作为所有职业的默认最优选择

### 暂缓 / TODO

- `领导术` 暂缓：原先“回合结束后概率额外获得一个新回合”的方案强度和规则改写程度都过高，暂不进入首轮通用被动池
- `独狼天赋` TODO：默认可行动两回合、默认属性值提高 40%、且要求队伍中只能有一个成员，多于一个时失效。该方案属于规则改写型专长，后续单独设计，不纳入普通通用池

### 第一版实际启用的通用被动名单

虽然当前已讨论出 6 个可行方向，但第一版 vertical slice 实际启用的通用被动先压缩为以下 4 个：

1. `自然愈合`
2. `冥想`
3. `收割回复`
4. `幸运汲取`

#### 第一版暂缓但保留设计

5. `DeathProof` 型被动
6. `过度自信`

#### 收缩理由

- `自然愈合`：最稳的长线推进保底
- `冥想`：最稳的法系资源循环
- `收割回复`：最贴 pure run 连战与击杀节奏
- `幸运汲取`：最能代表机会流 build，且规则比 `过度自信` 更直观

暂缓的两个原因：

- `DeathProof`：保命价值过高，过早开放容易影响第一版平衡
- `过度自信`：高风险高回报条件更复杂，第一版先不优先实现

### 第一版通用主动启用规则

当前先明确一条第一版边界：

- `通用主动` 机制在技能候选算法中保留接口
- 但第一版默认 `不启用实际通用主动技能`

这意味着：

- 技能三选一的第 3 个位置在第一版主要由 `通用被动` 承担
- 若未来要开放通用主动，只需往同一候选池中追加数据，不必重写算法

采用这一边界的原因：

1. 先保证职业主动技能树本身站得住
2. 避免通用主动过早抢占职业身份
3. 让第一版升级 UI 和候选池复杂度保持可控

## 待明确：技能三选一的第三个位置

当前已确认：

- 技能升级阶段采用 `技能三选一`
- 默认结构优先为：`2 个职业技能候选 + 1 个额外候选`

但这里的“第 3 个位置”尚未最终定稿，不能与前文已经确定的 `通用被动池` 混为一谈。

需要后续单独确认的是：

1. 第 3 个位置是否真的放 `通用主动技能`
2. 如果放，它与前文的通用被动池是什么关系
3. 如果不放，当前职业技能不足 2 个时应如何补位

在这个问题确认之前，不应把任何 `Mew` 的 `colorless_abilities` 直接视为第一版已确认的“通用技能池”。

## 装备与消耗品来源

本原型不采用“战后奖励三选一”作为主成长来源，而采用更贴近冒险的混合来源：

1. 怪物死亡掉落
2. 宝箱开启掉落
3. 商店购买
4. 探索过程中的地图掉落

这样做的目的有三个：

1. 保留战棋冒险中的现场收获感
2. 让路线、战斗表现和资源经营都能影响构筑
3. 让星图探索不只是通往下一场战斗的过道

## 推进压力

搜打撤中的“撤离张力”被拿掉后，本原型改用 `血量/资源磨损` 承担推进压力。

### 压力来源

- 角色 HP 损耗
- 技能资源损耗
- 消耗品库存消耗
- 连续遭遇后的恢复机会稀缺

### 设计目标

- 让玩家不是在问“能不能带出去”，而是在问“现在这支三人小队还能不能继续往前打”
- 让推进决策建立在小队整体状态上，而不是单角色数值上
- 让资源磨损成为推动路线权衡和补给选择的核心动力

### 风险边界

资源磨损不能退化成单纯的补给税。它必须让玩家感受到：

1. 当前路线值得冒险
2. 当前补给机会有真实价值
3. 当前小队状态会改变后续节点偏好

## 核心循环

本方向的最小有效循环如下：

1. 在星图上选择路线或节点
2. 进入战斗、事件、商店或补给机会
3. 获得技能、装备、消耗品或状态变化
4. 重新分配三人小队的资源与职责
5. 判断是否继续推进更高风险区域

这个循环的重点不再是“带出”，而是“当前 run 是否越来越成型”。

## 成功标准

本方向成立，至少要观察到以下信号：

1. 玩家愿意为了尝试另一种三人配置而立刻重开一局
2. 每次装备掉落都会产生“给谁穿”的真实讨论
3. 每次技能成长都会影响小队分工，而不是只提升个人效率
4. 星图路径选择会被当前小队状态影响
5. 资源磨损会改变玩家对战斗、商店和补给节点的偏好

补充正式判据：

- 在 pure run 三人小队原型中，一条路线或节点选择，只有在结算后不会把当前小队压缩到仅剩单一、被迫的后续解法，并且能够通过恢复、消耗品补充、技能/天赋/属性成长或经济转化，扩宽、恢复或强化下一轮的合理解法集合时，才应被视为当前 run 中的合理选择。
- 若一次结算能够稳定改变玩家下一轮的合理解法集合，使玩家既未被压缩为单一路径求生，又因 `HP/MP/死亡状态`、`消耗品变化`、`技能/天赋/属性成长`、`金币/商店机会` 中的一类或多类结果而主动重配三人职责、调整风险偏好或改写路线优先级，则可视为 pure run 的“三人构筑 -> 再选择”闭环开始成立。

## 失败标准

以下现象出现时，应视为该方向尚未成立：

1. 三人只是三个独立角色并排前进，没有协同构筑感
2. 装备只看品质与数值，不会引出分配决策
3. 技能成长只让角色更强，但不改变小队打法
4. 星图推进只是走格子，和当前小队状态弱相关
5. 资源磨损只让玩家烦躁，并没有制造有意义的策略压力

补充正式判据：

- 若结算结果虽持续发生，但既未改变三人小队下一轮的合理解法集合，也未促使玩家重新分配队内资源、重估路线风险或调整角色职责，则不应视为 pure run 构筑闭环成立。
- 若玩家在多次循环后仍长期沿用同一种路线逻辑，只把成长 action 当作数值增强，而不会因为新的技能/天赋/属性组合去主动挑战更高价值路线，或因为状态受损而转向更稳健路线，则说明小队构筑尚未进入地图决策层。

## 与搜打撤方案的本质差异

这条 pure run 方向，验证重点和原先搜打撤方案完全不同：

- 原方案问：玩家是否愿意为了带出收益承担风险
- 新方案问：玩家是否愿意为了尝试新构筑反复重开

- 原方案的奖励价值来自“可保存”
- 新方案的奖励价值来自“本局立刻改变打法”

- 原方案的高压点来自“亏不亏”
- 新方案的高压点来自“小队还能不能继续推进”

因此两者不能混着评估，必须用不同的成功标准看待。

## 对 Task 1 基线的替换说明

`2026-06-24-short-term-prototype-task1-design.md` 仍然保留为原始验证基线记录，但在 pure run 分支下，以下表述需要被替换理解：

1. `结算 -> 带出 -> 再入局` 改为 `节点收益 -> 小队重配 -> 继续推进`
2. `撤离张力` 改为 `血量/资源磨损压力`
3. `愿不愿意带出收益` 改为 `愿不愿意立刻重开尝试另一种构筑`

这样做的目的，是保留讨论历史，同时明确当前分支的验证口径已经变化。

## 原型阶段非目标

以下内容不应在本轮原型中优先证明：

- 完整职业阵容
- 大型装备池
- 复杂剧情与事件文本
- 长期局外解锁体系
- 精细数值平衡
- 正式终局内容

原型阶段只需要证明：三人小队的 run 内构筑是否足够让人反复开局。

## 技能分支数据结构字段表 v1

本节是实现前必须存在的字段级规格，用来承接：

- 职业技能分支
- 通用被动 / 通用主动候选池
- 技能前置与门槛过滤
- 技能链解锁与技能升级版候选

### 核心原则

- `技能分支节点` 是数据对象，不是纯 UI 概念
- 职业技能分支与通用候选共享同一套基础过滤字段
- `基础 / 高级 / 大师` 是技能阶段字段，不是靠命名约定推断
- “是否在第一版启用”必须显式可配，避免未实现内容误入候选池

### 建议字段

#### 标识字段

- `id`
  - 类型：`string`
  - 用途：专长唯一 ID，代码与存档用
  - 示例：`mage_fire_basic`

- `displayName`
  - 类型：`string`
  - 用途：显示名称

- `description`
  - 类型：`string`
  - 用途：面板描述文案

#### 归属字段

- `entryKind`
  - 类型：`enum`
  - 值：`CareerSkill` | `CommonPassive` | `CommonActive`
  - 用途：区分职业技能链与通用候选

- `career`
  - 类型：`enum?`
  - 值：`Mage` | `Necromancer` | `Amazon` | `None`
  - 用途：职业技能归属；通用候选填 `None`

- `branchId`
  - 类型：`string`
  - 用途：所属分支 ID
  - 示例：`fire_magic`、`undead_mastery`、`spear_mastery`

- `category`
  - 类型：`enum?`
  - 值示例：`Survival` | `Resource` | `CritOpportunity`
  - 用途：通用被动或通用主动类别；职业技能链可为空

#### 阶段字段

- `tier`
  - 类型：`enum`
  - 值：`Basic` | `Advanced` | `Master`
  - 用途：标识技能链阶段

- `upgradesFromSkillId`
  - 类型：`string?`
  - 用途：高阶技能链节点由哪个旧技能继续推进
  - 示例：`meteor` 的前置可能是 `summon_fire_imp`

#### 门槛与前置字段

- `mainAttribute`
  - 类型：`enum`
  - 值：`Strength` | `Agility` | `Constitution` | `Speed` | `Intelligence` | `Charisma` | `Luck`
  - 用途：该技能或候选的主属性门槛判断字段

- `attributeThreshold`
  - 类型：`int`
  - 用途：主属性门槛值
  - 当前统一规则：
    - `Basic = 5`
    - `Advanced = 7`
    - `Master = 9`

- `prerequisiteSkillIds`
  - 类型：`string[]`
  - 用途：进入候选池前必须拥有的前置技能
  - 说明：职业技能通常只需 0 或 1 个前置；通用被动可为空

#### 候选与升级字段

- `grantedAtRunStart`
  - 类型：`bool`
  - 用途：该基础技能是否可在 run 开局作为职业随机入场技能自动授予

- `unlockSkillIds`
  - 类型：`string[]`
  - 用途：该节点解锁进入候选池的后续技能列表
  - 说明：这些技能首次获取时占用 `技能三选一`

- `upgradeResultSkillId`
  - 类型：`string[]`
  - 用途：若本次候选代表的是某个旧技能的升级版，这里记录升级结果技能 ID
  - 说明：升级版仍作为技能候选出现，而不是自动赠送

#### 强化字段

- `enhancementSummaries`
  - 类型：`string[]`
  - 用途：UI 展示“该技能链阶段会强化哪些已有技能”的摘要
  - 说明：这是表现字段，不是执行字段

- `enhancementRules`
  - 类型：`object[]`
  - 用途：代码执行的强化规则表
  - 建议子字段：
    - `targetSkillId`
    - `enhancementType`：`Numeric` | `Rule`
    - `targetField`
    - `operation`：`Add` | `Multiply` | `Replace` | `AppendRule`
    - `value`
    - `note`

#### 候选池控制字段

- `enabledInFirstSlice`
  - 类型：`bool`
  - 用途：第一版是否允许进入候选池

- `isComplicated`
  - 类型：`bool`
  - 用途：是否属于复杂专长，可用于后续做复杂池分层

- `uiPriority`
  - 类型：`int`
  - 用途：同一批候选展示时的排序参考

#### 调试 / 说明字段

- `designNote`
  - 类型：`string?`
  - 用途：仅设计/策划备注，不参与运行时逻辑

### 最小示例

```json
{
  "id": "fireball",
  "displayName": "火球术",
  "description": "火系基础技能，作为法师火系入场技能。",

  "career": "Mage",
  "branchId": "fire_magic",

  "upgradesFromSkillId": null,
  "mainAttribute": "Intelligence",

  "prerequisiteSkillIds": [],
  "grantedAtRunStart": true,
  "unlockSkillIds": [],
  "upgradeResultSkillId": null,

  "enhancementRules": [],
  "enabledInFirstSlice": true,

```

### 第一版最低要求

第一版如果想开工，至少要先把以下字段真正落到数据层：

## 统一命名清单 v1

以下命名用于统一当前纯技能树版本的设计、计划、实现与 UI 文案。后续新增内容应优先复用这些术语，避免继续混用“专长版”旧词。

### 成长层术语

- `分支`
  - 含义：某个职业内部的一条成长路线
  - 示例：法师的 `火系分支`、死灵法师的 `亡灵支配分支`

- `基础技能 / 高级技能 / 大师技能`
  - 含义：同一条分支里的三个阶段节点
  - 说明：这里的“基础 / 高级 / 大师”是技能链阶段，不再是独立专长阶段

- `技能升级版`
  - 含义：已拥有技能的更高版本候选
  - 示例：`火球术 Lv2`、`突刺 Lv3`
  - 说明：升级版仍然作为技能候选出现，占用一次技能选择机会

### 候选层术语

- `职业技能候选`
  - 含义：来自当前职业技能分支、满足前置与属性门槛的候选技能

- `通用主动`
  - 含义：不定义职业身份、但可以进入技能三选一的主动技能

- `通用被动`
  - 含义：不定义职业身份、但可以进入技能三选一的被动技能

- `通用候选`
  - 含义：技能三选一里的第三个位置，可以是 `通用主动` 或 `通用被动`

### 入场与推进术语

- `入场技能`
  - 含义：run 开局时，职业随机获得的那条基础分支自动授予的技能

- `前置技能`
  - 含义：某个技能要进入候选池前必须已获得的技能

- `主属性门槛`
  - 含义：某个技能或通用候选进入候选池所要求的基础属性值

### UI 术语

- `自动升级提示`
  - 含义：展示本次升级中，已拥有技能出现升级版结果的提示区
  - 说明：它是展示层术语，不代表独立的成长步骤

- `技能三选一`
  - 含义：升级阶段的主要选择界面
  - 默认结构：`2 个职业技能候选 + 1 个通用候选`

### 应避免继续使用的旧术语

- `专长二选一`
- `职业专长池`
- `通用专长池`
- `基础专长 / 高级专长 / 大师专长`

这些词如果再出现，除非是在“旧规则对照”语境中，否则都应改写成当前纯技能树版本的术语。

## 九个基础技能参数总表 v1

### 法师

#### 火球术

- 主属性：`智力`

- 施法距离：`5 格`

- 命中方式：`projectile` 直线飞行，只有敌方单位阻挡

- 施法距离：`5 格`

- 命中方式：与火球术类似，遇到第一个敌方单位生效

- 形状：基础单体，后续可扩为 AOE

## 技能候选算法规则表 v1

本节把“升级时如何生成技能三选一候选”写成接近伪代码的实现前规格，供后续 `SkillSystem / SkillDatabase` 直接对照。

### 输入

- `character`
  - 当前升级角色
- `careerSkillPool`
  - 当前职业全部技能定义
- `commonPassivePool`
  - 第一版启用的通用被动定义
- `commonActivePool`
  - 第一版启用的通用主动定义（若第一版暂不开，则为空）

### 过滤条件

某个技能要进入候选池，必须同时满足：

1. 来源合法：
   - 要么属于当前角色职业技能池
   - 要么属于第一版启用的通用主动 / 通用被动池
2. `enabledInFirstSlice == true`
3. 当前角色基础属性满足该技能的 `mainAttribute` 门槛
4. 当前角色已拥有该技能要求的 `prerequisiteSkillIds`
5. 若该条目是技能升级版，则当前角色必须已拥有被升级的旧技能
6. 若该条目是大师技能，而第一版暂不实现，则直接排除

### 候选来源定义

- `职业技能候选池`
  - 来自当前职业技能定义
  - 包含：
    - 新技能候选
    - 已拥有技能的升级版候选

- `通用候选池`
  - 来自第一版启用的 `通用被动` + `通用主动`

### 候选生成规则（伪代码）

```text
function GenerateSkillChoices(character):
    careerPool = []
    commonPool = []

    for each skill in careerSkillPool:
        if not skill.enabledInFirstSlice:
            continue
        if skill.career != character.career:
            continue
        if not MeetsAttributeThreshold(character, skill):
            continue
        if not HasPrerequisiteSkills(character, skill):
            continue
        if skill.isMasterSkill and FirstSliceMasterDisabled:
            continue
        if skill.isUpgradeVersion and not CharacterHasBaseSkill(character, skill):
            continue
        careerPool.add(skill)

    for each common in commonPassivePool + commonActivePool:
        if not common.enabledInFirstSlice:
            continue
        if not MeetsAttributeThreshold(character, common):
            continue
        if not HasPrerequisiteSkills(character, common):
            continue
        commonPool.add(common)

    careerChoices = RandomPickUpToTwo(careerPool)
    commonChoices = []

    if careerChoices.count == 2:
        commonChoices = RandomPickUpToOne(commonPool)
    else:
        commonChoices = RandomPickUpTo(3 - careerChoices.count, commonPool)

    finalChoices = careerChoices + commonChoices

    if finalChoices.count < 3:
        finalChoices = FillRemainingWithFallback(finalChoices, character)

    return finalChoices
```

### 规则解释

#### 1. 升级版技能与新技能同权

- 在职业技能池内：
  - 新技能候选
  - 升级版技能候选
  完全平权随机，不额外加权。

#### 2. 第三个位置可以是通用主动或通用被动

- `通用候选` 不限于被动
- 可以来自：
  - `通用被动`
  - `通用主动`

#### 3. 职业技能不足时的补位规则

- 若职业技能候选池有 `2 个` 或以上：
  - 抽 `2 个职业技能候选`
  - 再抽 `1 个通用候选`

- 若职业技能候选池只有 `1 个`：
  - 组成 `1 个职业技能候选 + 2 个通用候选`

- 若职业技能候选池为 `0`：
  - 允许出现 `3 个通用候选`

#### 4. 升级版技能可再次出现

- 同一个技能的升级版允许在后续升级中再次出现，只要：
  - 该技能仍有更高升级版可选
  - 当前角色属性仍满足对应门槛

### UI 需要知道的最小输出

候选生成器最终至少返回给 UI 这些字段：

- `id`
- `displayName`
- `career / commonKind`
- `tier`
- `isUpgradeVersion`
- `upgradesFromSkillId`
- `description`
- `mainAttribute`
- `attributeThreshold`

## 升级结果落库顺序伪代码 v1

本节只解决一个问题：一场战斗结束后，升级相关的数据到底按什么顺序计算、展示、确认、写回。

目标是避免以下常见错误：

- 先生成技能候选，后加属性，导致本次加点无法影响当前候选
- UI 看起来选完了，但角色数据没有真正落库
- 技能升级版提示和新技能选择互相覆盖
- 最低等级角色的判定与结算顺序不稳定

### 输入

- `partyCharacters`
  - 当前队伍全部角色数据
- `battleResult`
  - 当前战斗结算结果
- `skillDatabase`
  - 职业技能池、通用主动池、通用被动池

### 高层流程

```text
OnBattleVictory()
    eligibleCharacters = GetAliveOrEligibleCharacters(partyCharacters)
    targetCharacter = SelectUpgradeTarget(eligibleCharacters)
    if targetCharacter == null:
        return

    GrantLevelUp(targetCharacter)
    OpenLevelUpFlow(targetCharacter)
    SaveCharacterAfterLevelUp(targetCharacter)
```

### 1. 选择谁升级

```text
SelectUpgradeTarget(characters):
    minLevel = Min(characters.level)
    lowest = Filter(characters, c => c.level == minLevel)
    if lowest.count == 1:
        return lowest[0]
    return RandomPickOne(lowest)
```

规则：

- 每场战斗后只允许 1 个角色升级
- 优先选当前等级最低的角色
- 若有多个同为最低等级，则随机 1 个

### 2. 授予升级资格

```text
GrantLevelUp(character):
    character.level += 1
    character.unspentAttributePoints += 1
```

说明：

- 第一版不做经验累计逻辑
- 每次升级固定只加 `1` 点属性点

### 3. 打开升级面板的状态准备

```text
OpenLevelUpFlow(character):
    preview = BuildLevelUpPreview(character)
    ShowLevelUpPanel(preview)
```

其中：

```text
BuildLevelUpPreview(character):
    autoUpgradePreview = CollectAutoUpgradePreview(character)
    attributeState = SnapshotCurrentAttributes(character)
    return {
        autoUpgradePreview,
        attributeState,
        skillChoices: []
    }
```

说明：

- `autoUpgradePreview` 只是提示，不先落库
- 此时还不能生成技能候选，因为属性点还没分配

### 4. 属性加点

```text
OnAttributeAllocated(character, attributeType):
    if character.unspentAttributePoints <= 0:
        reject
    ApplyAttributePoint(character, attributeType)
    RefreshSkillChoices(character)
```

关键规则：

- 属性点一旦分配，就立刻写回到角色的临时升级状态
- 这次加点必须立即影响本次技能候选

### 5. 生成技能三选一候选

```text
RefreshSkillChoices(character):
    choices = GenerateSkillChoices(character)
    ShowSkillChoices(choices)
```

其中 `GenerateSkillChoices(character)` 复用前一节的候选算法规则：

- 先从职业技能池取最多 2 个候选
- 再从通用池补到 3 个
- 新技能与升级版技能同权竞争

### 6. 玩家选择一个技能候选

```text
OnSkillChoiceConfirmed(character, selectedChoice):
    if selectedChoice.isUpgradeVersion:
        ApplySkillUpgrade(character, selectedChoice)
    else:
        LearnSkill(character, selectedChoice)
```

这里明确：

- 升级版技能与新技能用同一个确认入口
- 区别只在于落库时是 `升级已有技能` 还是 `添加新技能`

### 7. 处理自动升级提示

```text
CollectAutoUpgradePreview(character):
    previews = []
    for each ownedSkill in character.skills:
        nextUpgrade = FindImplicitPreviewOnlyUpgrade(ownedSkill, character)
        if nextUpgrade != null:
            previews.add(nextUpgrade)
    return previews
```

这里的约束是：

- 自动升级提示只负责“告诉玩家某条技能链后续可能如何成长”
- 真正发生升级仍然要通过 `技能三选一` 选中升级版候选来落库
- 因此提示与落库必须分开

### 8. 最终落库

```text
SaveCharacterAfterLevelUp(character):
    PersistCharacterState(character)
    PersistPartyState()
    CloseLevelUpPanel()
```

落库前必须已经完成：

1. 等级提升
2. 属性点消耗
3. 技能选择或技能升级

### 最小状态流总结

```text
战斗胜利
 -> 选出最低等级角色
 -> 等级+1，属性点+1
 -> 打开升级面板
 -> 展示自动升级提示（仅展示）
 -> 玩家分配属性点
 -> 系统按新属性刷新技能三选一
 -> 玩家选择一个技能候选
 -> 根据候选类型：学习新技能 / 升级已有技能
 -> 写回角色与队伍数据
 -> 关闭面板
```

### 第一版的关键实现断言

- 本次加点必须影响本次技能候选
- 自动升级提示本身不直接改数据
- 技能升级版与新技能通过同一个确认动作落库
- 若玩家没有完成属性加点，不能进入技能确认
- 若技能候选为空，必须有兜底逻辑或明确的 UI 提示

## 法师三系分支骨架 v1

- `火系基础阶段`

  - 功能技能候选：`召唤火魔`
